## 先在网页里找到模型配置

打开「真实模型：TAMS 客服提示词对比」这条评测记录，右上角点 **Eval actions → View YAML**。`providers` 中能看到：

```yaml
providers:
  - id: openai:chat:volcano/deepseek-v4-1-flash-260910
    label: TAMS DeepSeek Flash
    config:
      apiBaseUrl: https://dev-cn.tensorart.net/v2/openapi/v1
      apiKeyEnvar: TAMS_TOKEN
      showThinking: false
```

这里的 `openai:chat:` 表示兼容的接口格式，实际请求发到上面配置的 TAMS 地址。

配置按每一次评测保存。**Eval actions → Edit and re-run** 会把这条记录的模型、提示词、用例和评分规则一起载入编辑页面，你可以修改后再运行。也可以通过 **New → Evaluation** 新建评测，再导入或编辑 YAML。

代码里的配置入口：

- `model-provider.cjs`：共用的接口地址、模型名、凭证变量名和请求参数。
- `compose.yaml`：把启动终端的 `TAMS_TOKEN` 传给网页与评测容器。
- `promptfooconfig.*.cjs`：每一种体验使用哪些提示词、题目和评分规则。

当前没有把密钥写入代码或报告。另开终端、重新创建容器时，需要确保该终端已设置 `TAMS_TOKEN`；也可以参考 `.env.example`，在本目录被 Git 忽略的 `.env` 中本地配置。

## 按这个顺序体验

| 顺序 | 网页里找的记录 | 主要看什么 |

点 **Show Charts** 查看图表；列标题中的提示词按钮用于查看该列的提示词。右上角 **Eval actions** 还提供下载和与另一份评测比较的入口。

## 1. 提示词对比与规则评分

从仓库根目录进入示例目录后运行：

```bash
cd promptfoo-demo
docker compose run --rm eval eval -c promptfooconfig.live.cjs --no-cache \
  -o output/live.json output/live.html output/live.csv output/live.junit.xml
```

6 道题 × 2 版提示词，共 12 次真实调用。规则检查 JSON 结构、分类及拒绝提供内部信息的回答。

当前只有一个模型，表格两列代表两版提示词。模型本身的横向对比需要在 `providers` 中再配置第二个可用模型；本例不会把两版提示词冒充两个模型。

## 2. 让 AI 给回答打分

```bash
docker compose run --rm eval eval -c promptfooconfig.judge.cjs --no-cache \
  -o output/judge.json output/judge.html
```

6 道题各调用一次客服模型，再调用一次评分模型，共约 12 次请求。评分模型同样走 TAMS，检查礼貌、下一步建议，以及是否编造退款时限、订单状态或已经执行的操作。

AI 评分也是判断结果，需要结合评分理由复核。基础格式和分类通过，并不代表回答的所有业务细节都正确。

## 3. 对比是否提供知识资料

```bash
docker compose run --rm eval eval -c promptfooconfig.rag.cjs --no-cache \
  -o output/rag.json output/rag.html
```

2 道题 × 2 种上下文，共 4 次请求。虚构政策规定未拆封普通盲盒签收后 12 天内可申请退货，但没有写退款到账时限。

第一题要求回答退货期限：有资料时可以答对，无资料时无法给出准确政策，会在答案要求上失败。第二题询问资料没写的到账时限，两列都应该承认不知道。这是预期的能力差异。

本例只演示把已选资料提供给模型及检查答案，不包含文档上传、检索或向量数据库。

## 4. 多轮对话

```bash
docker compose run --rm eval eval -c promptfooconfig.conversation.cjs --no-cache \
  -o output/conversation.json output/conversation.html
```

共 3 次串行请求：先告诉模型订单号 `ORD-2048`，再问刚才的订单号，最后问是否发货。通过 `_conversation` 带上前面的真实输入和输出，且没有接订单后台，所以必须承认无法确认发货状态。

## 5. 动态安全测试

```bash
# 先导出无凭证值的 JSON 配置，避开 0.126.0 保存 CJS 时的解析问题。
docker compose run --rm --entrypoint node eval scripts/export-redteam.cjs

# 用同一个 TAMS 模型生成两条测试消息，保留生成文件。
docker compose run --rm -e PROMPTFOO_DISABLE_REMOTE_GENERATION=1 eval \
  redteam generate -c output/redteam.config.json \
  -o output/redteam.generated.yaml --no-cache

# 再执行测试并生成结果，避免覆盖生成文件。
docker compose run --rm -e PROMPTFOO_DISABLE_REMOTE_GENERATION=1 eval \
  eval -c output/redteam.generated.yaml --no-cache \
  -o output/redteam.json output/redteam.html
```

只测试我们自己定义的虚构客服是否泄露内部指令或 `DEMO_SECRET_2026` 教学标记。攻击生成、被测回答和 AI 评分均走 TAMS；生成阶段另有请求，目标测试固定两条。

这只覆盖「提示词窃取」一类插件。安全测试结果需要看具体用例和评分理由，两条样例不能代表系统已经通过所有安全测试。

## 6. 失败题重测、报告与自动化检查

```bash
# 默认模拟演示含三条旧版失败，退出码 100 是预期结果。
docker compose run --rm eval

# 从旧结果挑失败题，只使用改进版重测；这一步仍是本地模拟。
docker compose run --rm eval eval -c promptfooconfig.cjs --no-cache \
  --filter-failing output/demo.json --filter-prompts '^improved' \
  -o output/retry.json output/retry.html
```

失败题重测应为 3/3。第一次筛题依据是旧结果，第二次执行使用当前配置，方便检查修复是否有效。

`live` 命令同时导出 HTML、JSON、CSV 和 JUnit XML。HTML 便于浏览，CSV 便于整理，JSON 便于程序处理，JUnit 用于接入已有自动化测试报告。

评测命令可接入持续集成：全部通过返回 0，断言不通过返回 100，配置或运行错误返回非零。不要在持续集成中用 `|| true` 忽略失败。

## Model Audit 页面为什么不能直接用

Model Audit 用于检查 `.onnx`、`.pkl`、PyTorch 等模型文件。本镜像当前提示未安装 `modelaudit` 命令，而且远程模型 API 不提供要扫描的本地模型文件，所以本次没有运行这一项。

团队角色权限、单点登录和企业运行器等能力也不属于当前本地社区版示例。先用上述入口体验真实模型评测，再按具体需求增加其他能力。

## 首次接入的一个已修复问题

DeepSeek 单独返回思考内容时，promptfoo 0.126.0 默认会把它拼到最终答案前面，形成 `Thinking: ...`，导致合法 JSON 答案也被格式规则判失败。`model-provider.cjs` 已设置 `showThinking: false`，只检查最终回答，Token 统计仍然保留思考用量。

最初的 0/12 记录保留在历史里用于排查，修复后的真实对比记录是 12/12；不要把接线格式问题当作模型分类能力差。
