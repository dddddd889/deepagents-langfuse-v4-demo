DeepAgents 接入 Langfuse v4 完整演示

本例记录
  1. handle-order-question：用户完整问题、最终回答、用户编号、会话编号。
  2. 模型调用：模型输入输出、耗时，以及模型实际返回的 token 用量。
  3. query_order 工具：请求参数、返回结果、耗时、异常。

固定版本
  Langfuse 服务端：4.82.0。
  Langfuse Python SDK：5.2.0。
  DeepAgents：0.7.40。
  langchain-openai：1.8.3；langchain-deepseek：1.2.1。
  python-dotenv：1.2.4。
  PDF 文本提取：pypdf 7.1.1。
  Python：.python-version 和容器统一使用 3.12；项目最低支持 3.11。
  uv：Docker 固定 0.13.6；本地使用 0.13.6 或更新版本。
  pyproject.toml 声明直接依赖，uv.lock 锁定全部依赖及跨平台安装信息。
  ClickHouse：26.3.62.3；PostgreSQL：17；Redis：7。
  MinIO 跟随 Langfuse 官方 Compose，使用 cgr.dev/chainguard/minio:latest。

运行前准备
  安装 uv，并启动 Docker，确保 uv 和 docker compose 命令可用。
  uv 可管理项目虚拟环境及 Python 版本，无需手动创建或激活 .venv。
  准备支持工具调用的模型 API Key。本例默认使用 gpt-4.1-mini。
  订单查询工具使用内存中的固定数据，无需访问真实订单服务。

最快运行：基础设施和示例都使用容器
  在项目目录执行：
    uv sync --locked
    uv run --locked init_env.py

  打开生成的 .env，在本地填写 OPENAI_API_KEY。
  使用其他兼容 OpenAI 的模型服务时，修改 OPENAI_BASE_URL 和 OPENAI_MODEL。
  模型名称和服务地址应与该服务的接口一致，且模型需支持工具调用。
  默认所有浏览器访问地址都是 localhost，适用于本机演示。

  启动 Langfuse 和所有依赖：
    docker compose up -d --wait --wait-timeout 300

  等待成功后，运行一次 DeepAgent：
    docker compose run --rm --build demo

  普通 docker compose up 不会运行 demo 服务；demo 仅在上条命令显式调用时执行。
  Web 首次启动会自动创建演示组织、项目、API Key 和用户。
  脚本与服务端读取同一份 .env 中的项目密钥。

  浏览器打开 http://localhost:3000。
  登录邮箱见 .env 的 LOGIN_EMAIL；默认 demo@example.com。
  登录密码见 .env 的 LOGIN_PASSWORD。
  进入项目 DeepAgents Order Demo，打开脚本输出的追踪链接。

在页面核对内容
  最外层步骤 handle-order-question 的 Input：
    请调用 query_order 查询订单 ORD-1001，告诉我状态和快递单号。
  最外层步骤的 Output 是模型最终回答。

  找到名称为 query_order、类型为 tool 的步骤。
  Input 应包含：
    {"order_id":"ORD-1001"}
  Output 应包含：
    {
      "order_id":"ORD-1001",
      "found":true,
      "status":"已发货",
      "carrier":"顺丰",
      "tracking_no":"SF-DEMO-1001",
      "items":["无线鼠标"]
    }
  某些视图会把工具返回值包在 ToolMessage 中，展开 content 即可看到上述 JSON。
  通过 v4 Observations API v2 读取时，本例工具 output 为序列化的 ToolMessage；
  先解析外层 JSON，再解析 content 中的 JSON，即可取得 tracking_no 等业务字段。
  工具之前、之后分别有模型调用，记录模型选择工具以及生成最终回答的过程。
  使用 user-demo-001、conversation-demo-001 或 order-demo 标签可以筛选本次追踪。

也可以在宿主机运行 Python
  基础设施仍然通过 Docker Compose 启动，然后执行：
    uv sync --locked
    uv run --locked demo.py
  uv 会按 .python-version 选择 Python 3.12，并管理项目内的 .venv。
  该方式从 .env 读取 LANGFUSE_BASE_URL=http://localhost:3000。
  容器方式会自动改用 http://langfuse-web:3000，浏览器链接仍指向 localhost。

PDF 子代理协作示例
  沿用当前 DeepSeek、Langfuse 配置；只分析你提供的 PDF，不创建样例文件。
  将待分析文件保存到 input/，然后在项目目录执行：
    uv sync --locked
    uv run --locked pdf_demo.py --pdf input/你的文件.pdf
  也可以指定任意本地路径，或者在 .env 中设置 PDF_FILE_PATH。
  自定义问题和结果位置：
    uv run --locked pdf_demo.py --pdf input/你的文件.pdf --question "总结主要结论和风险，每项注明页码" --output output/pdf/my-analysis.md

  实际协作流程：
    pdf-main-agent -> task(subagent_type=pdf-reader-agent)
    -> pdf-reader-agent -> get_pdf_info / read_pdf_page
    -> 子 Agent 返回带页码的事实 -> 主 Agent 汇总分析。
  PDF 读取工具只提供给子 Agent，完整工具代码位于 pdf_tools.py。
  委派与主代理汇总代码位于 pdf_demo.py，公共模型配置位于 demo_common.py。
  程序检查实际 task 请求及返回、子代理读取事件和页码覆盖，未完整读取时明确报错。
  结果保存到 output/pdf/analysis.md，控制台同时输出 Langfuse 追踪链接。
  默认将原 PDF 作为 LangfuseMedia 附件上传，原文件仍保留在 --pdf 指定的位置。
  上传和下载检查成功后才调用模型；失败时停止运行，并记录 ERROR 和失败状态。
  打开控制台输出的追踪链接，选最外层 pdf-analysis-workflow：
    Input 的 pdf 字段和 Media 区域会显示 PDF 附件。
    点击附件，再选 Open in new tab 打开或下载原件。
    当前 Langfuse 4.82 页面提示 No inline preview，不提供页内 PDF 预览。
  Metadata 同时记录以下字段，可定位本地来源和对象存储位置：
    pdf_path：本次读取的 PDF 绝对路径。
    report_path：分析报告的绝对路径。
    pdf_storage=langfuse_media：附件由 Langfuse 媒体存储管理。
    pdf_upload_status：pending / uploaded / failed，分别表示等待、成功、失败。
    pdf_media_id：附件编号；pdf_size_bytes：原文件字节数。
    pdf_sha256：原文件的 SHA256；pdf_object_path：对象存储路径，不含临时签名参数。
  默认附件位于 MinIO 的 langfuse 桶、media/demo-project/ 前缀下；相同内容会复用附件。
  Docker 中的 pdf_path 是 /app/input 等容器路径，可按 Compose 挂载对应宿主机目录。
  路径与初始状态从工作流开始记录，处理失败也保留；旧追踪不会自动补上传附件。

  一次最多返回一页的 12000 个字符，长页通过 next_offset 继续读取。
  本例提取文字，不做图片识别或 OCR；无文字页会明确标出，扫描件需先 OCR。
  主代理、子代理及各自模型调用、工具参数和返回的页面文字均记录到 Langfuse。

  使用容器时，input/ 只读挂载为 /app/input，output/ 挂载为 /app/output。
  在 .env 设置 PDF_FILE_PATH=input/你的文件.pdf 后运行：
    env -u OPENAI_API_KEY -u OPENAI_BASE_URL -u OPENAI_MODEL -u OPENAI_EXTRA_BODY -u LANGFUSE_PUBLIC_KEY -u LANGFUSE_SECRET_KEY docker compose run --rm --build pdf-demo
  pdf-demo 只在显式运行时启动，普通 up 不会调用 PDF 模型。
  Compose 自动注入 LANGFUSE_MEDIA_PUBLIC_ENDPOINT 和 LANGFUSE_MEDIA_INTERNAL_ENDPOINT：
  浏览器使用 S3_PUBLIC_URL（默认 http://localhost:9090）；容器通过 http://minio:9000 上传和校验。
  pdf_media.py 保留原始签名 Host，只切换连接地址，避免容器误连自身 localhost。
  外接 ClickHouse 时，在 docker compose 后添加 -f compose.external-clickhouse.yaml。

按标记自动采集 PDF 数据集
  默认只分析和记录追踪；指定 --collect-dataset 才自动加入 pdf-qa-candidates：
    uv run --locked pdf_demo.py --pdf input/你的文件.pdf --collect-dataset
  数据集不存在时自动创建；真实 task 委派、页码覆盖检查和报告保存全部成功后才采集。
  每条案例保存：
    Input：question、filename，以及原 PDF 附件 pdf。
    Expected output：先留空，待人工核对后填写参考答案。
    Metadata：candidate_answer（本次模型回答）、reviewed=false、pdf_sha256 和采集来源。
    来源关联：本次 Trace ID 和最外层工作流节点 ID。
  按“PDF 原始字节的 SHA256＋原始问题”生成稳定编号；相同内容的文件改名也不会重复新增。
  重复项返回 skipped_existing，保留原案例的全部内容、参考答案和审核状态；不会更新候选答案。
  文件内容或问题改变时生成新案例。程序不把 reviewed=false 当成允许覆盖旧记录的条件。
  采集成功或跳过时，控制台打印条目编号和数据集链接，追踪 Metadata 同时记录状态。
  采集失败会明确报错并在追踪标记失败；已经完成的 Markdown 报告仍保留。

  容器运行时同样显式添加开关：
    env -u OPENAI_API_KEY -u OPENAI_BASE_URL -u OPENAI_MODEL -u OPENAI_EXTRA_BODY -u LANGFUSE_PUBLIC_KEY -u LANGFUSE_SECRET_KEY docker compose run --rm --build pdf-demo uv run --no-sync pdf_demo.py --pdf input/你的文件.pdf --collect-dataset
  在 Langfuse 打开 Datasets -> pdf-qa-candidates，查看 Input.pdf 的原件和 Metadata.candidate_answer。
  人工核对后填写 Expected output，并在 Metadata 将 reviewed 改为 true。
  数据集包含原 PDF 附件；按当前 Langfuse 功能范围，完整 Agent 评测需使用 SDK 实验执行代码。

使用 DeepSeek 的 OpenAI 兼容接口
  继续使用 OpenAI 格式的 Chat Completions 接口，在当前终端提供 DEEPSEEK_API_KEY 后，修改本地 .env：
    OPENAI_API_KEY=${DEEPSEEK_API_KEY}
    OPENAI_BASE_URL=https://api.deepseek.com
    OPENAI_MODEL=deepseek-flash
    OPENAI_EXTRA_BODY={"thinking":{"type":"enabled"}}
  密钥引用会在运行时解析，无需将实际密钥写入 .env。
  OPENAI_EXTRA_BODY 是本例读取的额外请求体配置；本配置开启思考模式，主、子代理共用。
  DeepSeek 模型使用 ChatDeepSeekWithThinking：基于官方 LangChain 适配器接收思考内容，
  并在后续工具请求中回传 reasoning_content。关闭思考可把 enabled 改为 disabled。
  deepseek_model.py 提供兼容处理源码；其他模型仍使用 ChatOpenAI。
  在相同终端执行 uv run --locked demo.py 即可运行。
  使用容器运行时，确保 Compose 命令继承 DEEPSEEK_API_KEY，并排除其他项目的配置覆盖：
    env -u OPENAI_API_KEY -u OPENAI_BASE_URL -u OPENAI_MODEL -u OPENAI_EXTRA_BODY -u LANGFUSE_PUBLIC_KEY -u LANGFUSE_SECRET_KEY docker compose run --rm --build demo

外接已有的自建单机 ClickHouse
  使用 compose.external-clickhouse.yaml，文件中没有本地 ClickHouse 服务及其依赖。
  先在 .env 中修改：
    CLICKHOUSE_URL=http://你的地址:8123
    CLICKHOUSE_MIGRATION_URL=clickhouse://你的地址:9000
    CLICKHOUSE_USER=langfuse
    CLICKHOUSE_PASSWORD=对应密码
    CLICKHOUSE_DB=langfuse
  使用 TLS 时，HTTP 改为 https 和 8443，TCP 改为 9440，
  同时设置 CLICKHOUSE_MIGRATION_SSL=true。
  Docker 容器中的 localhost 指容器自己，应填写容器能访问的数据库地址。

  由数据库管理员创建专用库及用户，可参考 clickhouse-init.sql。
  执行前将 SQL 中的密码占位符改为与 .env 一致。
  该授权 SQL 面向自建单节点；ClickHouse Cloud 应参照官方权限清单单独授权。
  ClickHouse 至少为 25.12，服务器时区必须为 UTC。
  然后执行：
    docker compose -f compose.external-clickhouse.yaml up -d --wait --wait-timeout 300
    docker compose -f compose.external-clickhouse.yaml run --rm --build demo
  外接后 Langfuse 仍使用自己的表；已有业务日志需另行转换导入。

停机和再次运行
  停止服务并保留数据：
    docker compose down
  使用外接版本时，每条管理命令都带 -f compose.external-clickhouse.yaml。
  再次启动与运行沿用同一份 .env。
  SALT、ENCRYPTION_KEY 和数据库密码与已保存数据相关，首次初始化后保留原值。
  init_env.py 遇到已有 .env 会退出并保留原配置。

常见排查
  启动时提示大量变量未设置：先在项目目录运行 uv run --locked init_env.py，
  生成 .env 后再启动 Compose。激活 .venv 只切换 Python 环境，不会生成 .env。
  如果 .env 已存在，先执行 docker compose --env-file .env config --quiet 检查，
  不要删除已有密钥重新初始化。
  终端中已有 LANGFUSE_PUBLIC_KEY 或 LANGFUSE_SECRET_KEY 时，Compose 会优先使用它们。
  如需使用本项目 .env 的密钥，在 up 或 run 命令前加上：
    env -u LANGFUSE_PUBLIC_KEY -u LANGFUSE_SECRET_KEY
  本地 demo.py 以项目 .env 为准，容器中的示例使用 Compose 注入的配置。
  本例直接使用 Docker Hub 上的官方 Langfuse 镜像，版本仍为 4.82.0。
  官方说明同名标签与 docker.langfuse.com 的镜像摘要相同；直接拉取可减少一个网络入口。
  拉取镜像时报 no such host 或 no route to host：检查 Docker Desktop 的网络及代理，
  再执行 docker compose --progress plain pull 查看下载进度。
  --wait-timeout 300 限制的是容器就绪等待，不限制此前的镜像下载时间。
  基础设施未就绪：
    docker compose ps
    docker compose logs --tail=100 langfuse-web langfuse-worker
  认证失败：先等待 Web 健康，再检查 .env 中的密钥是否与当前项目匹配。
  找不到追踪：检查脚本最后是否打印 Trace ID，并确认用户所在项目和时间范围。
  工具没有执行：检查是否使用支持工具调用的模型；脚本会明确报错。
  模型返回 401/404：核对 OPENAI_API_KEY、OPENAI_BASE_URL 和 OPENAI_MODEL。
  端口冲突：修改 Compose 中的宿主机端口，并同步 NEXTAUTH_URL、S3_PUBLIC_URL、
  LANGFUSE_BASE_URL、LANGFUSE_PUBLIC_URL 中对应的端口。

实现要点
  CallbackHandler 采集 DeepAgents 内部的模型与工具事件。
  外层 start_as_current_observation 显式保存用户问题和最终回答。
  propagate_attributes 将用户、会话和标签传给子步骤。
  finally 中的 flush 确保短脚本退出前发送已缓冲的追踪数据。
  query_order 本身没有再加 observe，避免同一次工具调用重复记录。

压缩、Skill、MCP 与评估的完整样例
  宿主机入口：full_trace_demo.py。运行前先启动本地 Langfuse，沿用项目 .env 模型配置。
  完整运行会调用真实模型；2026-11-24 已按用户要求执行，并从 Langfuse 回读核对。
  后续执行命令：
    uv sync --locked
    uv run --locked full_trace_demo.py
  可指定评估报告保存目录：
    uv run --locked full_trace_demo.py --output-dir output/full-trace

  本轮任务：通过 MCP 查询 ORD-1001 的订单与物流，保留历史选择的联系渠道。
  程序注入明确标记的演示历史，达到 12 条消息阈值后，由 DeepAgents 原生中间件
  将旧消息交给真实模型写摘要，保留最近 4 条消息；这是方便观察的演示阈值。
  原始历史由原生中间件写到本轮 StateBackend 的 /conversation_history/，
  摘要和最近消息进入后续模型上下文；这些虚拟文件随本次图状态存在，不是磁盘文件。
  context_compression 仅在真正调用摘要模型时建节点，不把每次阈值检查算成压缩。
  输入记录被摘要的消息，输出记录实际摘要；估算 token 数只放 Metadata，
  不混进模型实际用量或费用。真实模型用量由 CallbackHandler 在 generation 上记录。

  demo_skills/order-status/SKILL.md 定义查询步骤和最终 JSON 五个字段。
  文件注入 StateBackend，通过原生 pinned_skills 加载到模型消息，skill.load 记录正文。
  full_trace_mcp_server.py 是独立的本地订单 MCP 服务，固定版本 mcp==2.3.0。
  Agent 使用同一虚拟环境启动子进程，通过 stdio 完成发现、查询与返回值校验。
  query_order_mcp 是 Agent 的工具节点，内部 mcp.call_tool 表示 MCP 协议调用边界。
  MCP 返回值由 OrderLookupResult 定义明确的结构；未知订单返回 found=false。

  在 Tracing 筛选 full-trace-demo 标签，打开输出链接中的 Trace，核对关键节点：
    order-full-trace-workflow：完整用户问题、最终回答及完成次数。
    mcp.discover_tools：实际发现的 MCP 工具与输入输出结构。
    skill.load：实际加载的 Skill 正文。
    context_compression -> generation：压缩输入、摘要及写摘要的模型调用。
    query_order_mcp -> mcp.call_tool：工具参数、协议返回结果和错误。
    evaluate-order-answer：规则评估结果。
  框架还会记录模型选择工具、生成回答、tools 批次等中间节点。
  回调在当前协程内执行，手动记录的 MCP 节点继承对应工具的父子关系。

  评估以 BOOLEAN Scores 关联最外层节点，0 表示失败，1 表示通过：
    answer_format：最终回答是仅含 Skill 指定五个字段的 JSON 对象。
    order_accuracy：订单字段与本次 MCP 成功返回的订单一致；没有实际查询不通过。
    compression_fact_retention：摘要和最终回答都保留历史联系渠道“在线客服”。
    workflow_execution：实际执行了压缩、Skill 正文加载和 MCP 查询。
  这些是固定任务的代码规则检查；事实保留规则检查关键词，不评价泛化摘要质量。
  所有规则完成后，报告保存到 output/full-trace/<trace_id>.json，
  包含回答、实际执行记录、评估分数和 Trace 链接；评估不通过时程序以非零状态退出。
  节点执行异常会标记 ERROR，并由 finally 发送缓冲区；不会伪造成功结果。

  自定义面板统计压缩次数：选择 Observations，Metric 选 Count，
  用 Observation Name = context_compression 筛选。名称是本样例上报的名称，
  并非 Langfuse 内置的“压缩”指标。失败执行也有节点，需要成功次数时排除 ERROR。
  根节点 Metadata 的 compression_count 则只统计成功写出非空摘要的次数。

  不调用真实模型、不写入 Langfuse 的验证命令：
    uv run --locked python -m unittest discover -s tests -p 'test_full_trace.py' -v
